## 진우 매니저 캐싱 문의 (응답 대기)

**진우 질문**: "캐싱 구현이 로컬상에서 캐싱인지, 백엔드 캐싱(Redis 등)인지?"

**답변 초안 (사용자가 전달 예정)**:
- 이번 구현 = Next.js `unstable_cache` 인메모리 캐시, Lambda 인스턴스 자체 메모리 사용
- Redis 같은 분산 캐시 아님
- 50명 × 300건 규모 + 인스턴스 수 적을 것 예상 → 단일 인스턴스 hot path 최적화 + 60s TTL 목적

**솔직히 인지한 한계 (Lambda 멀티 인스턴스 환경)**:
- 각 Lambda 인스턴스가 자기 메모리에 독립적으로 cache → 인스턴스별 격리
- 한 인스턴스에서 `revalidateTag` 호출해도 다른 인스턴스는 stale 유지 (broadcast 안 됨)
- cold start 시 캐시 비어 있음 → 첫 요청 DB hit
- mutation 직후 다른 인스턴스로 라우팅되면 stale 데이터 가능
- DB 부하 절감 효과: 95%는 과장, 50-80% 절감이 현실적
- mutation 즉시 반영은 본인 요청을 같은 Lambda가 처리할 때만 보장

**분산 캐시 필요 시 옵션**:
- OpenNext incremental cache handler를 S3/DynamoDB/Redis 백엔드로 설정
- 모든 Lambda 인스턴스 같은 캐시 공유
- `revalidateTag` broadcast 동작
- 추가 인프라 작업 필요 (OpenNext config + IAM)

**진우 결정 대기 항목**:
1. 현재 인메모리 구현 그대로 유지
2. OpenNext incremental cache handler 분산 캐시로 업그레이드 (S3/DynamoDB/Redis)
